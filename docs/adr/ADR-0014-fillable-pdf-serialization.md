# ADR-0014: Fillable PDF serialization strategy

## Status

Accepted for implementation

## Context

The Studio already has a browser-native static print/PDF path and now has explicit multiline text-field and checkbox-field publication blocks. The next milestone is a genuinely fillable PDF whose controls remain editable in a PDF viewer.

The browser `window.print()` API only opens the user agent print dialog and does not provide an application-level contract for creating PDF AcroForm fields. The existing print path therefore remains the static-output path rather than becoming the fillable serializer.

A fillable serializer must:

- run in the browser;
- create multiline text fields and checkboxes explicitly;
- preserve the existing publication authoring model;
- reuse derived publication layout rather than creating another editorial model;
- avoid storing reader responses in Studio publication state;
- remain independent from React rendering.

## Decision

Use `pdf-lib` as the first fillable PDF serialization dependency.

`pdf-lib` is a TypeScript/JavaScript PDF library that runs in browsers and exposes PDF form APIs including `PDFForm.createTextField()` and `PDFForm.createCheckBox()`. Form widgets can be positioned on a specific PDF page with explicit coordinates and dimensions.

The browser print path remains available as **Print / Save as PDF** for static output.

A separate **Download fillable PDF** path will serialize the same `PublicationLayout` into PDF bytes and add AcroForm widgets for interactive publication blocks.

## Serialization boundary

The serializer receives publication/layout data and returns PDF bytes. It must not read React component state or DOM geometry directly.

The first implementation maps:

- `multiline-text-field` → PDF text field configured for multiline input;
- `checkbox-field` → PDF checkbox field.

Field names must be deterministic and unique. The initial naming contract is based on publication ID plus durable block ID rather than prompt text so editing a label does not change the field identity.

## Geometry strategy

The serializer uses US Letter page coordinates derived from the existing document settings and layout page sequence.

The initial PDF serializer may use the same deterministic block-height estimation already used by `PublicationLayout`. Pixel-perfect parity with the HTML preview is not required for the first foundation, but page ordering, margins, content order, cover, page numbering, and field placement must remain structurally consistent.

Measurement-based pagination can later replace estimates without changing the authored publication model.

## Consequences

Static browser print and fillable binary PDF become two intentional export modes instead of one overloaded mechanism.

The dependency is introduced only at the export boundary; editor, persistence, revision history, and preview stay library-agnostic.

The first fillable serializer can be tested by loading generated bytes and inspecting AcroForm field names/types without relying only on manual viewer testing.

Manual validation in common PDF viewers remains required before calling the fillable export production-ready.
