# ADR-0014: Fillable PDF serialization boundary

## Status

Accepted

## Context

Browser-native print is appropriate for static PDF output, but the Studio also needs PDFs whose multiline text fields and checkboxes remain interactive after download.

The authoring model, automatic pagination, and publication preview already share a derived `PublicationLayout`. Binary PDF generation must not introduce a second publication-domain model or push PDF-library concepts into the editor.

The selected serializer must work in the browser, support creating PDF forms, support multiline text fields and checkboxes, and serialize directly to bytes.

## Investigation

`pdf-lib` is an MIT-licensed TypeScript/JavaScript library designed for browser and Node environments. Its public form API supports creating text fields and check boxes, adding field widgets to pages, enabling multiline text fields, and saving the document to a `Uint8Array`.

The project has a mature form API and browser examples. Its latest official tagged release is older than the Studio's application stack, so the integration should remain isolated behind a narrow export boundary and covered by generated-PDF tests rather than allowing library types to spread through the publication domain.

## Decision

Use `pdf-lib` as the initial fillable-PDF serializer candidate for the MVP, behind a publication-owned export contract.

Introduce a library-independent `PublicationPdfPlan` before adding the serializer dependency. The plan owns:

- exact US Letter geometry in PDF points: 612 × 792;
- the fixed Gentle Page margin: 54 points (0.75 inch);
- derived page sequence and content-page numbering;
- stable interactive field names derived from publication and block IDs;
- field kind, authored label, and derived content page assignment.

The serializer will consume this plan and the existing derived publication layout. It must not read editor state directly.

Browser `Print / Save as PDF` remains the static export path. Fillable PDF becomes a separate binary-export action.

## Form-field mapping

- `multiline-text-field` → AcroForm text field with multiline enabled;
- `checkbox-field` → AcroForm check box;
- field names use `publication.<publicationId>.block.<blockId>` to remain stable and collision-resistant inside one export.

## Consequences

The project can replace the PDF library later without changing publication persistence, editor APIs, or interactive block types.

Exact field widget coordinates and document drawing remain serializer concerns. They should be derived deterministically from the same Letter geometry and pagination rules used by preview.

The first implementation should validate generated bytes by loading the result and checking field names/types before exposing the export action in the UI.
